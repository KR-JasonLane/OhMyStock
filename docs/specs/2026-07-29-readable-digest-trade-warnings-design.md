# Telegram 다이제스트 거래 경고 요약 설계

- 작성일: 2026-07-29
- 상태: 사용자 설계 승인
- 범위: 16:10 Telegram 장 마감 다이제스트의 거래 경고 표시

## 1. 목표

현재 거래 엔진은 진입하지 않은 이유와 실행 중 이상을 `trade_runs.warnings`에
영속하지만, 장 마감 다이제스트는 주문·포지션·손익 집계만 표시한다. 그 결과
`최종 진입 후보 1종목`, `매수 주문 0건`이 함께 보여도 왜 주문하지 않았는지
Telegram만으로 알 수 없다.

DB의 감사 원문과 거래 로직은 유지하면서, 거래일에 발생한 경고를 운영자가
이해할 수 있는 한국어 요약으로 최대 5건 표시한다.

## 2. 범위 밖

- 종목 수집·스코어링·AI 분석·최종 후보 선정 변경
- 유동성·갭·보유 중복·슬롯·시간창 등 진입 기준 변경
- 주문·체결·포지션·손익 계산 변경
- `trade_runs.warnings` 저장 방식 또는 DB schema 변경
- 경고 원문 삭제·수정
- 실제 주문이나 분석 재실행

## 3. 사용자 표시

대표 메시지는 다음과 같다.

```text
💼 자동매매
매수 주문        0건
매도 주문        0건
현재 관리 포지션 0개
실현손익         0원 (추정)

⚠️ 오늘 발생한 거래 경고
- AI 분석 지연 후 정상 복구
- 003960 · 유동성 기준 미달 (2.53억 / 기준 10억)
```

거래 경고가 없으면 이 절은 표시하지 않는다. 계좌·파이프라인 누락을 보여주는
기존 `⚠️ 확인 필요` 절은 별도로 유지한다.

## 4. 경고 선택과 순서

- 해당 다이제스트 거래일과 실행환경에 속한 모든 `trade_runs.warnings` 행을
  시간순으로 읽는다.
- 각 행의 개행 구분 경고를 구조화된 안전 코드로 정규화한다.
- 같은 코드·종목·수치 조합은 한 번만 표시한다.
- 최대 5건을 표시한다.
- 고유 경고가 5건을 넘으면 마지막에 `- 외 N건`을 추가한다.
- 경고는 원래 발생 순서를 유지한다.
- 과거 catch-up 다이제스트도 해당 거래일의 영속 경고만 사용한다.

## 5. 안전한 경고 매핑

DB 경고 원문은 Telegram payload나 본문에 그대로 복사하지 않는다. 저장
adapter가 허용된 형식만 구조화하고 presenter가 고정 한국어 문구를 만든다.

### 5.1 분석 준비

| DB 경고 유형 | 사용자 표시 |
|---|---|
| 분석 결과 없음·기준일 불일치 후 당일 분석 성공 | `AI 분석 지연 후 정상 복구` |
| 분석 결과 없음·기준일 불일치가 끝까지 미해소 | `AI 분석 결과를 제때 사용하지 못함` |
| 신선한 분석의 최종 후보 0개 | `AI 최종 진입 후보 없음` |

복구 여부는 경고 문자열만으로 추정하지 않는다. 같은 다이제스트의 pipeline
요약에서 분석 성공과 올바른 기준일이 확인될 때만 `정상 복구`로 표시한다.

### 5.2 후보 진입 차단

| DB 경고 유형 | 사용자 표시 |
|---|---|
| 유동성 하한 미달 | `{종목코드} · 유동성 기준 미달 ({관측값} / 기준 {하한})` |
| 신호가 대비 현재가 갭 초과 | `{종목코드} · 가격 변동폭 기준 초과` |
| 이미 보유 중 | `{종목코드} · 이미 보유 중이라 진입하지 않음` |
| 재진입 쿨다운 | `{종목코드} · 재진입 대기시간 적용` |
| 포지션 슬롯 또는 자금 한도 | `{종목코드} · 포지션 또는 자금 한도 적용` |
| 시세·진입 context 누락 | `{종목코드} · 진입 판단 자료 부족` |
| 가격 결측 | `{종목코드} · 가격 정보 확인 불가` |

금액은 정수 원 단위로 구조화한 뒤 억 원 단위 사용자 문구로 표시한다.
`252,557,535`는 `2.53억`, `1,000,000,000`은 `10억`으로 표시한다. 종목코드는
기존 허용 형식만 표시하며 종목명은 경고 원문에서 추출하지 않는다.

### 5.3 실행·감시 경고

| DB 경고 유형 | 사용자 표시 |
|---|---|
| 발주 직전 시세 재조회 실패 후 기존 시세 사용 | `최신 시세 재조회 실패 · 기존 시세 사용` |
| quote 조회 연속 실패·누락 | `보유 포지션 시세 조회 불안정` |
| 주문·체결·대사 상태 확인 필요 | `주문 또는 체결 상태 확인 필요` |
| kill switch·scheduler·dead letter | 기존 전용 상태 문구를 유지하고 중복 표시하지 않음 |

## 6. 알 수 없는 경고

- 허용 패턴과 일치하지 않는 원문은 외부로 노출하지 않는다.
- 알 수 없는 경고가 하나 이상이면 `일부 거래 상태 확인 필요` 한 건으로
  통합한다.
- 알 수 없는 원문의 개수는 전체 초과 건수 계산에는 포함한다.
- 원문은 기존 `trade_runs.warnings`에 남아 SQL과 운영 로그로 복기한다.

## 7. 데이터 모델과 호환성

domain에 제한된 경고 DTO를 둔다.

```python
@dataclass(frozen=True)
class DigestTradeNotice:
    code: str
    symbol: str | None = None
    observed_krw: int | None = None
    threshold_krw: int | None = None


@dataclass(frozen=True)
class DigestSection:
    facts: Mapping[str, str | int | bool | None]
    as_of: datetime | None
    failed_fields: tuple[str, ...] = ()
    notices: tuple[DigestTradeNotice, ...] = ()
    notice_count: int = 0
```

- `notices`는 최대 5개이며 `notice_count`는 중복 제거 후 전체 경고 수다.
- pipeline section은 빈 notices를 사용하고 trading section만 값을 채운다.
- `Digest.payload` version은 1을 유지하면서 section에 `notices`와
  `notice_count`를 선택 필드로 추가한다.
- 기존 version 1 retained payload에 두 필드가 없으면 빈 경고로 읽는다.
- 새 payload는 경고 코드·종목코드·허용된 정수만 저장하고 DB 원문을 담지 않는다.
- 실제 `/digest`는 기존처럼 저장된 delivery part를 그대로 재전송하므로 과거
  메시지는 재작성되지 않는다.

## 8. 데이터 흐름

1. `DigestRunStore.trading_summary()`가 해당 거래일·환경의 trade run과 경고를
   읽는다.
2. store adapter의 정규화 함수가 각 원문을 허용된 `DigestTradeNotice`로
   변환한다.
3. 알 수 없는 원문은 단일 generic notice로 축약한다.
4. `Digest` presenter가 pipeline 성공 여부와 함께 분석 지연의 복구 상태를
   판정한다.
5. Telegram 본문에는 최대 5건과 `외 N건`만 표시한다.
6. payload와 delivery part는 기존 durable outbox 경로로 저장·전송된다.

## 9. 오류 처리와 보안

- 자유 텍스트 경고를 domain 또는 Telegram에 전달하지 않는다.
- 종목코드·금액 파싱 실패는 generic notice로 fail-closed한다.
- 음수 금액, 과도한 자릿수, 지원하지 않는 code는 DTO 생성 단계에서 거부한다.
- 경고 정규화 실패가 다이제스트 전체 생성을 중단시키지 않도록 해당 항목만
  generic notice로 격리한다.
- DB 조회 자체가 실패하면 기존 digest 생성 실패 경계를 유지하며 불완전한
  본문을 전송하지 않는다.
- 본문은 기존 plain-text 분할과 Telegram 길이 상한을 그대로 사용한다.

## 10. 검증

- 오늘 실측 원문 두 건을 fixture로 사용하되 실제 운영 원문 전체를 문서나
  소스에 복사하지 않는다.
- 분석 지연 후 성공과 미복구를 구분한다.
- 유동성 관측값·하한을 억 원 단위로 표시한다.
- 갭·보유 중복·쿨다운·슬롯·자료 부족·시세·주문 상태 매핑을 검증한다.
- 중복 제거, 발생 순서, 최대 5건과 `외 N건`을 검증한다.
- 알 수 없는 원문·파싱 실패가 외부에 노출되지 않는지 검증한다.
- 기존 version 1 payload와 새 선택 필드 payload를 모두 retained renderer가
  읽는지 검증한다.
- 기존 delivery part 원문 재전송 계약을 유지한다.
- 전체 Telegram 알림과 비라이브 회귀를 실행한다.

## 11. 배포와 수용

배포 뒤 다음 정상 16:10 모의 다이제스트에서 거래 경고 절을 확인한다.
`/digest`는 그 메시지를 읽기 전용으로 다시 조회한다. 경고를 만들기 위해
분석·주문·제어 명령을 수동 실행하지 않는다.
