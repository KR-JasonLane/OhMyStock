# 아침 AI 분석 Telegram 요약 설계

- 작성일: 2026-07-27
- 상태: 사용자 설계 승인
- 범위: 성공한 아침 AI 분석 결과의 단일 운영자 Telegram 요약과 최근
  분석·거래 다이제스트 조회 명령

## 1. 요청과 목표

매 거래일 아침 AI 분석이 성공하면 운영자가 Telegram에서 시장 판단과 진입
후보를 한눈에 확인할 수 있어야 한다. 전체 20개 종목의 상세 원문을 그대로
보내지 않고 다음 정보만 읽기 쉬운 한국어 요약으로 전달한다.

- 실행 환경(`mock` 또는 `real`)
- 시장 국면과 시장 요약
- 최대 진입 권고 종목 수
- 최종 진입 후보와 각 후보의 승인 이유·위험 요소
- AI가 승인했지만 최대 종목 수 제한으로 최종 후보에서 제외된 차순위 종목
- 전체 승인·거절 수
- 최종 후보 없음 안내
- 실제 주문 전에 별도 거래 방어선을 적용한다는 고지

운영자는 자동 알림을 놓쳤거나 나중에 다시 확인하고 싶을 때 다음 읽기 전용
명령을 사용할 수 있어야 한다.

- `/analysis`: 가장 최근 성공한 아침 AI 분석 요약
- `/digest`: 보존 중인 가장 최근 16:10 거래 다이제스트

Telegram 장애나 프로세스 재기동이 분석 성공을 실패로 바꾸면 안 된다. 같은
분석을 중복 전송해서도 안 되며, 당일 분석 완료 뒤 재기동하더라도 아직 보내지
않은 요약은 복구 전송해야 한다.

## 2. 범위 밖

- AI 분석 알고리즘, 프롬프트, 후보 선정 순서 변경
- 유동성·가격 갭·거래정지·자금 한도 등 거래 방어선 변경
- 최종 후보가 없을 때 AI 재호출 또는 대체 후보 자동 진입
- Telegram을 통한 분석 실행·재실행 또는 다이제스트 재생성 명령
- 20개 종목의 모든 거절 이유 전송
- 계좌번호, 자격 증명, 주문 원문 응답 전송
- 외부 모델 또는 LangSmith 텔레메트리 추가

## 3. 선택한 구조

### 3.1 대안 비교

1. **AnalysisService가 Telegram을 직접 호출**
   - 장점: 성공 직후 바로 호출할 수 있다.
   - 단점: Telegram 장애가 분석 경로에 결합되고 durable retry·중복 방지 책임이
     분석 계층으로 누출된다.
   - 판정: 사용하지 않는다.

2. **스케줄러가 고정 시각에 최신 분석을 조회**
   - 장점: 구현이 단순하다.
   - 단점: 분석 지연·재시도와 고정 시각이 경합하고, 누락 복구와 중복 방지를
     다시 구현해야 한다.
   - 판정: 사용하지 않는다.

3. **Telegram 서비스가 DB의 성공한 분석을 감지해 durable outbox로 물질화**
   - 장점: 기존 sender의 lease, retry, 분할 전달, 중복 방지, 재기동 복구를
     재사용한다. 분석 실행과 알림 전달의 장애 경계도 분리된다.
   - 단점: 짧은 폴링 지연이 생긴다.
   - 판정: 채택한다.

### 3.2 계층 경계

- `store/`: 성공한 분석 run과 verdict를 읽는 전용 read model, 이미 생성된
  요약의 idempotency 확인, outbox·delivery 원자 물질화
- `domain/notifications/`: 분석 요약 값 객체, 선택 규칙, 한국어 presenter
- `core/telegram_service.py`: bounded poll loop 또는 기존 composite tick에
  분석 요약 서비스를 조립
- 기존 Telegram command parser·query worker: `/analysis`, `/digest` 읽기 전용
  명령과 `/help` 설명을 추가
- `domain/analysis/`: 변경하지 않는다.
- `adapters/kiwoom/`, 주문 경로: 변경하지 않는다.

분석 저장과 알림 outbox 생성을 하나의 트랜잭션으로 강제하지 않는다. 대신
성공한 분석 run을 DB에서 반복 조회하고 idempotency key로 한 번만 물질화하여
프로세스가 어느 지점에서 종료돼도 최종적으로 복구한다.

## 4. 감지와 중복 방지

### 4.1 대상

- `status='succeeded'`인 분석만 대상이다.
- 현재 `run_environment`와 동일한 분석·스코어링 데이터만 사용한다.
- 당일 거래일에 시작된 분석만 즉시 요약한다.
- 서비스 중단 뒤 재기동하면 당일의 미전송 성공 분석을 오래된 순서로 복구한다.
- 과거 여러 날의 메시지를 갑자기 보내지 않도록 catch-up 범위는 당일로 제한한다.

### 4.2 idempotency

요약의 고유 키는 다음 형식이다.

```text
analysis-summary:{run_environment}:{analysis_run_id}
```

같은 키의 outbox가 있으면 다시 생성하지 않는다. outbox와 모든 delivery part는
하나의 DB 트랜잭션으로 생성한다. sender retry는 새 outbox를 만들지 않고 기존
delivery 상태를 전이한다.

### 4.3 순서와 상한

- 한 tick에서 처리할 분석 run 수를 제한한다.
- 오래된 `analysis_run_id`부터 처리한다.
- 메시지 분할은 기존 Telegram formatter의 UTF-8/길이 계약을 사용한다.
- 한 분석 요약이 완전히 전송되지 않은 상태에서 같은 분석의 새 요약을 만들지
  않는다.

## 5. read model과 표시 규칙

### 5.1 필요한 필드

- 분석: run id, status, regime, market summary, max picks advice,
  score reference date, started/finished time
- verdict: symbol, verdict, confidence, reasons, risk flags, picked, pick rank
- 종목: symbol, 표시 이름
- 환경: mock 또는 real

표시 이름을 읽지 못하면 종목코드만 사용하고 메시지 생성을 실패시키지 않는다.
깨진 JSON reasons/risk flags는 해당 필드를 `확인 불가`로 표시하고 나머지
요약은 전달한다. 행 손상 수와 누락 필드는 내부 경고와 메시지 하단에 남긴다.

### 5.2 분류

- **최종 후보**: `picked=true`, `pick_rank` 오름차순
- **차순위 승인**: `verdict='approve'`지만 `picked=false`
- **거절**: `verdict='reject'`

차순위 승인은 confidence 내림차순, 종목코드 오름차순으로 결정론적으로 정렬한다.
Telegram 길이를 제한하기 위해 차순위 승인은 최대 3개만 표시하고 전체 개수는
별도로 표시한다.

### 5.3 이유와 위험 요소 상한

- 최종 후보별 승인 이유: 최대 2개
- 최종 후보별 위험 요소: 최대 2개
- 차순위 후보: 종목명·코드와 최종 제외 이유만 표시
- 개별 문자열은 formatter에 전달하기 전에 길이를 제한한다.

모델 출력 문자열은 Telegram HTML/Markdown으로 해석하지 않고 plain text로
전달한다. 사용자·모델 입력이 parse mode나 링크를 주입하지 못하게 한다.

## 6. 메시지 형식

### 6.1 최종 후보가 있는 경우

```text
🧠 아침 AI 분석 완료 · 모의투자

시장 국면  중립
최대 진입 권고  1종목

시장 요약
AI 관련 호재로 반등을 시도하고 있지만 시장 방향성과 주요 업종 흐름은
아직 불분명합니다.

🎯 최종 후보
007160 · 사조산업
- 전략점수와 업종점수가 상대적으로 높음
- Pullback 전략 기대수익이 거래비용을 상회

주의
- 시장 방향성 불분명
- 전략 표본이 충분히 크지 않음

📋 차순위 승인
475150 · SK이터닉스
- AI는 승인했지만 최대 1종목 제한으로 최종 제외

검토 결과  승인 2 · 거절 18

※ AI 분석 결과이며 실제 주문 전 유동성·가격 갭·거래정지·자금 한도
방어선을 다시 확인합니다.
```

### 6.2 최종 후보가 없는 경우

```text
🧠 아침 AI 분석 완료 · 모의투자

시장 국면  위험회피
오늘 최종 진입 후보가 없습니다.

검토 결과  승인 0 · 거절 20
자동매매는 신규 진입 없이 대기합니다.

※ AI 분석 결과이며 실제 주문 여부는 거래 방어선이 최종 결정합니다.
```

`mock`은 `모의투자`, `real`은 눈에 띄는 `실전`으로 표시한다. 알 수 없는 환경은
메시지를 만들지 않고 fail-closed한다.

## 7. 조회 명령

### 7.1 명령 계약

| 명령 | 의미 | 부수효과 |
|---|---|---|
| `/analysis` | 가장 최근 성공한 AI 분석을 자동 알림과 같은 presenter로 다시 표시 | 없음 |
| `/digest` | 아직 본문이 보존된 가장 최근 16:10 거래 다이제스트를 그대로 표시 | 없음 |

두 명령은 기존 단일 운영자 인증을 통과한 private chat에서만 처리한다. 확인
토큰이나 상태 변경 command intent를 만들지 않으며, 실제 분석·계좌 조회·주문을
새로 실행하지 않는다. 응답은 기존 query 우선순위와 durable outbox 경로를 사용해
Telegram 일시 장애에도 재시도한다.

`/help`의 조회 절에 다음 두 줄을 추가한다.

```text
/analysis   최근 AI 분석
/digest     최근 거래 다이제스트
```

### 7.2 `/analysis`

- `status='succeeded'`인 가장 최근 분석 run을 읽는다.
- 자동 알림과 동일한 read model·presenter를 사용해 두 형식이 어긋나지 않게 한다.
- 분석이 한 번도 성공하지 않았다면 `조회 가능한 AI 분석이 없습니다.`라고
  표시한다.
- 명령 시점에 AI를 다시 호출하거나 후보를 재선정하지 않는다.

### 7.3 `/digest`

다이제스트에는 생성 당시 계좌 스냅샷과 당일 거래 결과가 포함된다. 명령 시점의
현재 계좌를 다시 조회해 과거 다이제스트와 섞으면 의미가 바뀌므로 재계산하지
않는다. 기존 `digest` outbox·delivery에서 보존 중인 가장 최근 전송 본문을
그대로 읽는다.

- 현재 환경과 일치하는 가장 최근 `digest`만 선택한다.
- delivery part 순서를 유지해 기존 분할 본문을 재전송한다.
- 민감 본문 TTL이 지나 scrub됐거나 생성된 다이제스트가 없으면
  `조회 가능한 최근 거래 다이제스트가 없습니다.`라고 표시한다.
- TTL을 늘리거나 scrub된 계좌 스냅샷을 복원하지 않는다.
- 조회 자체가 원본 digest outbox의 전송 상태나 보존기한을 변경하지 않는다.

기본 보존기간이 24시간이므로 `/digest`는 최근 당일 다이제스트 재확인을 위한
명령이다. 장기 성과 조회는 SQL read model과 대시보드가 담당한다.

## 8. 실패와 복구

- 분석의 중간 `running` 또는 일시 `failed` 상태는 보내지 않는다.
- 스케줄러가 분석 가능 시간 안에서 재시도해 성공하면 성공 결과만 한 번 보낸다.
- 최종 실패·gave-up 알림은 이번 태스크 범위에서 새로 만들지 않는다. 기존
  scheduler-dead·운영 이상 알림과 중복 의미를 설계한 뒤 별도 태스크로 다룬다.
- read model 조회 실패는 분석 run이나 verdict를 변경하지 않고 다음 tick에
  재시도한다.
- outbox 물질화 뒤 Telegram 전송 실패는 기존 sender의 429, 일시 오류, 영구
  오류 정책을 그대로 따른다.
- 재기동은 당일 미전송 성공 분석을 복구하되 이미 생성된 idempotency key는
  건너뛴다.

## 9. 보안과 보존

- 분석 요약은 운영자의 매매 신호이므로 `sensitive=true`로 저장한다.
- payload와 delivery body는 24시간 TTL 뒤 scrub한다.
- 종목코드·종목명·모델 요약 외 계좌, 토큰, 앱키, 주문 응답을 포함하지 않는다.
- 로그에는 본문 전체를 남기지 않고 analysis run id, idempotency key, 상태,
  part 수만 남긴다.
- 단일 운영자 인증과 Telegram sender의 기존 경계를 변경하지 않는다.
- `/analysis`, `/digest` 응답도 기존 query TTL과 민감 payload scrub 정책을
  따른다.

## 10. 테스트와 수용 기준

### 10.1 순수 테스트

- final pick, 차순위 승인, 거절 수를 정확히 분류한다.
- final pick과 차순위 정렬이 결정론적이다.
- 이유·위험 요소·차순위 표시 상한을 지킨다.
- 후보 없음, 종목명 없음, 손상 JSON을 안전하게 표시한다.
- mock/real 표기가 명확하고 알 수 없는 환경은 거부한다.
- 모델 문자열이 plain text로 유지되고 Telegram 길이 분할을 통과한다.
- parser가 `/analysis`, `/digest`를 정확히 구분하고 인자·변형 명령을 기존
  command 문법대로 처리한다.

### 10.2 저장소·서비스 테스트

- 성공한 당일 분석만 선택한다.
- 같은 idempotency key는 outbox를 한 번만 생성한다.
- outbox와 delivery parts가 원자적으로 생성된다.
- materialize 직전·직후 재기동에도 누락·중복이 없다.
- 당일 미전송 분석은 복구하고 과거일 분석은 갑자기 보내지 않는다.
- DB 조회 실패는 다음 tick 재시도로 복구한다.
- 민감 payload와 body가 TTL 뒤 scrub된다.
- `/analysis`가 최근 성공 run만 읽고 자동 알림과 같은 본문을 만든다.
- `/digest`가 현재 환경의 최신 보존 body를 part 순서대로 읽는다.
- digest 없음·scrub·다른 환경만 존재하는 경우 unavailable로 응답한다.
- 두 조회 명령이 분석·계좌·주문 adapter를 호출하지 않는다.

### 10.3 통합·비라이브 수용

- 합성 분석 fixture로 Telegram adapter 직전 delivery body를 확인한다.
- 실제 Telegram·키움 API·주문을 호출하지 않는 전체 회귀를 통과한다.
- scheduler·analysis·trading 서비스의 기존 생명주기와 종료 순서가 유지된다.
- `/help`에 두 조회 명령이 표시되고 기존 명령과 충돌하지 않는다.
- 네 전문 관점 리뷰에서 Critical·Important 0을 확인한다.

### 10.4 실제 Telegram 수용

비라이브 검증과 리뷰 완료 뒤 사용자의 별도 승인을 받아 모의환경에서만 수행한다.
새 분석을 임의 재실행하지 않고, 저장된 합성 또는 다음 정상 아침 분석 한 건으로
다음만 확인한다.

- 성공 분석 뒤 요약 1회 도착
- 재기동·중복 tick에도 추가 전송 없음
- Telegram 일시 장애 뒤 durable retry
- 최종 후보와 차순위 승인, 환경, 방어선 고지의 가독성
- `/analysis`가 같은 분석을 재실행하지 않고 최근 요약을 반환
- `/digest`가 생성 당시 다이제스트를 재계산 없이 반환
- scrub된 다이제스트가 명확한 unavailable 응답을 반환

실제 주문과 상태 변경 명령은 실행하지 않는다.

## 11. 완료 조건

- 분석 성공이 Telegram 장애와 독립적이다.
- 성공한 당일 분석 요약이 결국 한 번 전달된다.
- 최종 후보·차순위 승인·승인/거절 수가 DB 원자료와 일치한다.
- 후보가 없어도 억지 추천 없이 명확한 대기 메시지를 보낸다.
- `/analysis`, `/digest`가 부수효과 없이 최근 보존 결과를 재조회한다.
- 기존 보안·TTL·sender retry·분할 전달 계약을 재사용한다.
- 비라이브 전체 회귀와 필수 리뷰를 통과한다.
