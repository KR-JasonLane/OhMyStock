# Phase 7 반응형 웹 대시보드 설계

- 작성일: 2026-07-26
- 상태: 사용자 설계 승인
- 범위: 조회 전용 운영 대시보드
- 선행 조건: Phase 6 자동 일정·거래 엔진과 Phase 8 Telegram 운영 기능

## 1. 목적

OhMyStock 자동매매의 성과와 현재 관리 상태를 PC·태블릿·모바일
브라우저에서 확인할 수 있는 반응형 웹 대시보드를 제공한다.

기존 Phase 0 Electron 셸은 제거하고 React 단일 페이지 애플리케이션(SPA)으로
전환한다. 프런트엔드와 FastAPI는 독립적으로 빌드·배포하되, 외부에서는
Tailscale HTTPS 주소 하나만 사용한다. 초기 버전은 조회 전용이며 대시보드
장애가 자동매매 런타임에 영향을 주어서는 안 된다.

## 2. 확정 결정

1. Electron 대신 React 브라우저 애플리케이션을 사용한다.
2. 프런트엔드와 FastAPI는 같은 서버의 서로 다른 컨테이너로 운영한다.
3. 외부 접근은 Tailscale tailnet 내부의 HTTPS로 제한한다.
4. 프런트엔드 컨테이너가 정적 파일을 제공하고 `/api`만 내부 FastAPI로
   역방향 프록시한다.
5. 화면은 모바일 우선 반응형으로 구현한다.
6. PrimeReact를 UI 기반으로 사용하되 OhMyStock 전용 디자인 토큰과
   레이아웃을 적용한다.
7. 라이트·다크 테마는 시스템 설정을 따르고 사용자가 수동 전환할 수 있다.
   선택값은 브라우저에 저장한다.
8. 최초 진입과 기간 변경 때 조회하며 자동 폴링과 WebSocket은 사용하지
   않는다.
9. 이후 갱신은 명시적 새로고침 버튼과 모바일의 당겨서 새로고침으로
   수행한다.
10. 기본 조회 기간은 최근 30일이며 임의 시작일·종료일 선택을 지원한다.
11. 성과에는 OhMyStock이 소유·관리한 자동매매 거래만 포함한다. 수동 거래와
    외부 보유분은 제외한다.

## 3. 범위

### 3.1 포함

- 기간별 핵심 성과와 누적 손익 추이
- 현재 관리 포지션
- 최근 관리 거래와 구조화된 청산 사유
- 시스템·데이터 기준시각과 조회 상태
- 모바일·태블릿·데스크톱 반응형 화면
- 라이트·다크 테마
- 버튼 및 모바일 당겨서 새로고침
- Tailscale 내부 HTTPS 접근

### 3.2 제외

- 거래 시작·중지·재개·청산 등 제어 기능
- 브라우저의 거래 API 키 또는 브로커 자격 증명 보관
- 계좌 전체나 수동 거래를 자동매매 성과에 합산
- 실시간 WebSocket 스트림과 자동 폴링
- 외부 인터넷 공개와 다중 사용자 권한 관리
- 대시보드 조회 과정의 키움 API 호출

향후 실시간 갱신이나 제어 기능을 추가할 수 있도록 데이터 접근 계층과
표현 계층을 분리하지만, 초기 구현에는 해당 기능을 미리 만들지 않는다.

## 4. 배포 아키텍처

```text
PC·모바일 브라우저
        │
        │ Tailscale Serve HTTPS
        ▼
프런트엔드 컨테이너
  ├─ /        React SPA 정적 파일
  └─ /api/*   내부 역방향 프록시
                    │
                    ▼
              FastAPI 컨테이너
                    │
                    ▼
                PostgreSQL
```

- 프런트엔드와 백엔드는 독립 이미지, 테스트, 배포 단위다.
- 브라우저에는 하나의 origin만 노출해 CORS와 자격 증명 전달 범위를
  단순화한다.
- 프런트엔드 호스트 포트와 FastAPI 포트는 `127.0.0.1`에만 바인딩한다.
- PostgreSQL은 외부에 공개하지 않는다.
- Tailscale Serve가 프런트엔드의 루프백 포트만 HTTPS로 전달한다.
- 프런트엔드 컨테이너가 중단돼도 backend와 scheduler는 계속 동작한다.
- SPA 경로 fallback과 `/api` 프록시는 명시적으로 분리해 API 오류를
  `index.html` 응답으로 숨기지 않는다.

## 5. 백엔드 읽기 모델

### 5.1 엔드포인트

초기 화면은 다음 전용 읽기 API 하나를 사용한다.

```http
GET /dashboard/overview?from=YYYY-MM-DD&to=YYYY-MM-DD&timezone=Asia/Seoul
```

프런트엔드 프록시를 통과할 때의 공개 경로는
`/api/dashboard/overview`다. 백엔드의 계층 경계는 다음과 같다.

- `api/`: 쿼리 검증과 응답 DTO
- `domain/`: 성과 계산 규칙과 상태 의미
- `store/`: SQL 조회와 읽기 모델 조립

엔드포인트는 저장된 주문·체결·관리 포지션·감사 데이터를 읽으며 BrokerPort나
키움 API를 호출하지 않는다. 벤더 원문 필드는 응답에 노출하지 않는다.

### 5.2 응답 영역

- 조회 기간과 KST 기준시각
- 데이터 최신 기준시각과 시세 경과시간
- 확정 손익, 평가손익, 총손익
- 확정 수익률, 청산 거래 수, 승·패·보합 수, 승률
- 기간별 누적 확정 손익 시계열
- 현재 관리 포지션
- 최근 청산 거래와 청산 사유
- 비용 반영 상태와 조회 실패 또는 손상 데이터 경고

금액과 비율은 표시용 문자열이 아니라 정밀 숫자와 상태를 반환하고,
원화·퍼센트 포맷은 프런트엔드가 담당한다.

### 5.3 계산 규칙

- **확정 손익**: 조회 기간 안에 청산이 확정된 관리 거래의 실현손익 합계
- **평가손익**: 현재 관리 포지션의 최신 저장 가격을 사용한 미실현손익 합계
- **총손익**: 확정 손익과 사용 가능한 평가손익의 합
- **확정 수익률**: 기간 내 청산 거래의 총 진입 체결금액 대비 확정 손익
- **승률**: 손익이 확정된 청산 거래 중 손익이 0보다 큰 거래의 비율
- **기간 귀속**: 진입일과 무관하게 청산 확정일이 조회 기간에 포함되면
  확정 성과에 포함
- **누적 곡선**: 조회 기간 내 청산 확정 순서대로 확정 손익을 누적
- **거래 단위**: 같은 관리 포지션의 분할 체결은 포지션 생애주기 하나로
  집계하며 주문 행 수를 거래 수로 세지 않음
- **비용**: 현재 `realized_pnl`은 프로젝트 비용 모델이 반영된 추정값이므로
  `cost_basis=estimated`로 표시하며, 실제 브로커 비용과 완전 대사된 값처럼
  표현하지 않는다(사용자 결정 2026-07-26). 청산 행에 `realized_pnl`이 없어
  비용 계산 자체가 불가능한 경우만 `cost_basis=unavailable`로 표시한다.

평가손익의 최신 가격이 없거나 신선도 기준을 넘으면 `0`이 아니라
`unavailable`로 반환한다. 이 경우 총손익도 완전한 값으로 가장하지 않고
부분값임을 상태로 명시한다.

## 6. 화면 설계

### 6.1 정보 구조

하나의 운영 대시보드로 시작한다.

1. **상단 바**
   - OhMyStock
   - 모의투자 환경 표시
   - 시스템 상태
   - 테마 전환
   - 새로고침
2. **기간 선택**
   - 시작일·종료일
   - 최근 7일, 최근 30일, 이번 달 빠른 선택
3. **핵심 성과**
   - 확정 손익
   - 평가손익
   - 총손익
   - 확정 수익률
   - 거래 횟수
   - 승률
4. **누적 손익 추이**
5. **현재 관리 포지션**
6. **최근 거래**
7. **마지막 갱신 시각과 데이터 경고**

계좌 예수금은 자동매매 성과와 섞지 않는다. 후속 요구가 생기면
`계좌 참고 정보` 영역으로 분리해 표시한다.

### 6.2 반응형 규칙

- 데스크톱: 핵심 지표를 한 행 또는 넓은 그리드로 배치하고 포지션·거래는
  PrimeReact DataTable로 표시한다.
- 태블릿: 지표와 차트를 2단 그리드로 재배치하고 표의 비핵심 열을 줄인다.
- 모바일: 지표는 2열, 표는 종목별 요약 카드로 전환한다.
- 모바일에서 가로 스크롤을 핵심 정보 탐색 수단으로 사용하지 않는다.
- 터치 대상은 충분한 크기와 간격을 유지한다.
- 금액은 줄바꿈으로 의미가 훼손되지 않게 축약 표기와 전체값 접근을 함께
  제공한다.

### 6.3 갱신 상호작용

- 화면 최초 진입과 기간 변경 시 한 번 조회한다.
- 새로고침 버튼과 당겨서 새로고침은 동일한 query 함수를 호출한다.
- 당겨서 새로고침은 모바일에서 문서가 최상단이고 아래 방향 제스처일 때만
  활성화한다.
- 임계 거리 전에는 진행 표시만 하고, 임계 거리를 넘긴 뒤 놓을 때 조회한다.
- 실행 중 추가 갱신은 병합해 중복 요청을 만들지 않는다.
- 성공 시 데이터와 마지막 갱신 시각을 원자적으로 교체한다.
- 실패 시 마지막 성공 데이터를 유지하고 오류 배너를 표시한다.
- 당김 동작을 지원하지 않는 환경에도 새로고침 버튼을 항상 제공한다.

## 7. 디자인 시스템

PrimeReact를 컴포넌트 기반으로 사용하되 기본 데모나 완성 템플릿을 그대로
복제하지 않는다.

- PrimeReact theme token 위에 OhMyStock 의미 토큰을 정의한다.
- 시스템 설정을 초기 테마로 사용하고 수동 선택은 브라우저에 저장한다.
- 총손익을 가장 강하게 강조하고 보조 지표는 단계적으로 대비를 낮춘다.
- 수익·손실·중립·경고 색은 라이트와 다크에서 동일한 의미를 유지한다.
- 숫자에는 tabular numeral을 적용해 자릿수 변화로 레이아웃이 흔들리지
  않게 한다.
- 과한 그라데이션, 장식용 아이콘, 형광색 카드, 깊은 그림자를 사용하지
  않는다.
- Skeleton은 실제 화면 구조와 같은 모양으로 제공한다.
- 빈 상태, 데이터 확인 불가, 조회 장애를 서로 다른 표현으로 구분한다.
- 접근 가능한 대비, 키보드 포커스, 레이블, reduced-motion 설정을
  보존한다.

주요 컴포넌트 후보는 DatePicker, Button, DataTable, Tag, Skeleton,
Toast와 접근 가능한 overlay다. 차트는 프로젝트 구현 계획에서 PrimeReact
호환성과 번들 크기, 접근성 대체 표현을 확인한 뒤 확정한다.

## 8. 오류·손상 데이터 처리

- 초기 조회 실패: 전체 오류 상태와 재시도 버튼을 표시한다.
- 갱신 실패: 기존 화면을 유지하고 비차단 오류 배너를 표시한다.
- 부분 데이터 실패: 성공한 영역은 표시하고 해당 영역만 `확인 불가`로
  표시한다.
- 빈 거래·포지션: 정상 빈 상태로 표시한다.
- 손상 행: 집계에서 임의 보정하지 않고 제외 수와 경고를 반환한다.
- stale 가격: 값과 기준시각을 함께 표시하거나 신선도 기준을 넘으면
  확인 불가로 처리한다.
- API 응답에는 내부 예외 메시지, SQL, 자격 증명, 브로커 원문을 넣지 않는다.

대시보드는 어떤 실패에서도 주문, scheduler, Telegram 상태를 변경하지
않는다.

## 9. 보안

- tailnet 밖에서 접근할 수 있는 공개 호스트 포트를 만들지 않는다.
- Tailscale Serve HTTPS와 tailnet ACL을 외부 접근 경계로 사용한다.
- 읽기 API만 프런트엔드 프록시에 허용한다.
- 브라우저 localStorage에는 테마처럼 비민감한 UI 설정만 저장한다.
- 거래 제어 토큰, 키움 키, Telegram 토큰, 계좌 식별자는 번들·로그·응답에
  포함하지 않는다.
- 운영 API의 쓰기 경로는 대시보드 내비게이션과 프록시 공개 범위에서
  제외한다.
- 프런트엔드 의존성은 고정 버전과 lockfile로 재현 가능하게 관리한다.

단일 운영자와 Tailscale 경계가 현재 전제다. 외부 공개나 복수 사용자를
도입할 때는 애플리케이션 인증·인가와 세션 보호를 별도 설계한다.

## 10. 검증 전략

### 10.1 백엔드

- 기간 경계와 Asia/Seoul 날짜 처리
- 기간 전 진입·기간 내 청산 귀속
- 분할 체결의 단일 포지션 생애주기 집계
- 승·패·보합과 승률
- 수수료·세금 완전·불완전 상태
- stale 가격, 빈 데이터, 손상 행, 부분 실패
- BrokerPort와 외부 API를 호출하지 않는 회귀

### 10.2 프런트엔드

- 기본 최근 30일과 사용자 지정 기간
- 라이트·다크 시스템 연동, 수동 전환과 저장
- 최초 조회, 기간 변경, 버튼·당김 갱신
- 중복 갱신 병합과 실패 시 이전 데이터 유지
- 로딩, 빈 상태, 확인 불가, 오류의 구분
- 모바일 카드와 데스크톱 DataTable의 동일 정보 의미

### 10.3 통합·수용

- 프런트엔드 프록시를 통한 읽기 API
- SPA fallback과 API 오류 응답 분리
- 프런트 중단이 backend 자동운용에 영향을 주지 않음
- 모바일·태블릿·데스크톱 대표 폭의 시각 확인
- Tailscale 연결 PC와 모바일의 HTTPS 접속
- 저장된 운영 데이터만 사용하며 키움 API와 실제 주문은 호출하지 않음

검증 명령은 변경 범위에 맞춰 backend의 `uv run pytest`와 frontend의
`pnpm lint`, `pnpm test`, `pnpm typecheck`, production build를 포함한다.
