# Telegram 명령 응답 가독성 개선 설계

## 1. 배경과 목표

Phase 8 실제 모의 수용에서 Telegram 명령의 송수신과 단일 운영자 인증은
정상 동작했다. 그러나 응답에는 `enabled=True`, `status=idle`,
`2026-07-25T15:06:00+00:00`처럼 내부 필드명·영문 상태·UTC 시각이 그대로
노출되어 운영자가 한눈에 상태를 판단하기 어려웠다.

`/account`는 `kt00001`에서 이미 조회한 예수금 `Deposit.total`을 버리고
주문가능금액만 표시했다. 또한 `kt00018.tot_evlt_amt`는 보유주식의
총평가금액인데 이를 사용자가 요청한 계좌 총자산처럼 오해할 여지가 있었다.
현재 프로젝트 실측 근거에는 계좌 전체 총자산으로 확정된 브로커 필드가 없다.

이 변경의 목표는 다음과 같다.

- 모든 Telegram 명령 응답을 핵심 요약형으로 통일한다.
- 정상 상태는 짧게, 주의·장애 상태는 원인만 선택적으로 상세 표시한다.
- 예수금·주문가능금액·보유주식 평가액의 의미를 구분한다.
- 검증되지 않은 총자산을 임의 계산하지 않고 `확인 불가`로 표시한다.
- 금액·시간·상태 표현을 한국 운영자가 즉시 이해할 수 있게 정규화한다.
- 기존 명령 실행, 확인, 복구, 감사, 민감정보 보호 계약은 유지한다.

## 2. 범위

### 2.1 포함

- `/status`, `/account`, `/positions`, `/help`
- `/pause`, `/stop`, `/resume`, `/liquidate_all`, `/confirm`
- 위 명령의 성공, 확인 필요, 실패, 기존 결과 재표시 응답
- 금액, 시각, 상태, 누락값의 공통 표시 규칙
- 계좌 요약에 예수금 추가

### 2.2 제외

- 체결·주문·스케줄러 운영 이벤트 알림의 본문
- 16:10 장 마감 다이제스트
- Telegram Bot API 호출 방식과 plain text 전송 계약
- 키움 TR 요청·응답 매핑과 추가 브로커 호출
- 총자산 추정 산식 도입
- 거래 또는 스케줄러 제어 의미론 변경

운영 알림과 다이제스트는 기존 상관 ID, 분할, 지연 표지 계약을 그대로
유지한다. 이번 작업은 사용자가 직접 요청한 명령 응답만 다룬다.

## 3. 설계 원칙

### 3.1 핵심 요약형

정상 상태는 운영자가 결론을 먼저 읽도록 `✅`, `⚠️`, `🚨` 아이콘과 짧은
한국어 문구를 사용한다. 내부 진단값은 정상일 때 숨긴다. `dead`,
`degraded`, backoff, kill switch, 손상 행처럼 조치가 필요한 값만 해당
구성요소 아래에 표시한다.

### 3.2 검증된 금액만 확정적으로 표시

- `Deposit.total`: `예수금`
- `Deposit.available`: `주문 가능`
- `Balance.total_eval`: `보유주식 평가`
- `Balance.total_profit`: `평가손익`
- 현재 환경의 당일 영속 거래 집계: `오늘 실현손익`
- 계좌 전체 총자산: `확인 불가`

예수금과 보유주식 평가액을 더한 값은 결제 예정 금액, 미수 등 계좌 상태를
충분히 반영한다고 검증되지 않았다. 따라서 합계를 총자산으로 표시하지
않는다. 향후 키움 실측으로 계좌 전체 자산 필드 또는 산식을 확정하면
`AccountSummary.total_assets`의 원천과 정확도 계약을 별도 설계한다.

### 3.3 안전한 plain text

Telegram Markdown/HTML parse mode를 추가하지 않는다. 동적 종목명과 상태가
마크업으로 해석되거나 전송 실패를 만드는 위험 없이 기존 plain text,
상관 ID, 길이 분할, 민감 payload TTL 삭제 계약을 유지한다.

## 4. 구조

### 4.1 프레젠터 분리

`app/domain/notifications/presentation.py`에 외부 의존 없는
`TelegramCommandPresenter`를 둔다. 이 객체는 명령 결과 데이터를 받아
문자열만 반환한다.

`CommandProcessor`는 다음 책임만 유지한다.

- durable inbox와 intent 상태 전이
- 공용 operations control 호출
- 위험 명령 확인 토큰 처리
- 실행 lease, 복구, 감사

표시 문구는 프레젠터로 위임한다. 명령 처리와 표현 변경을 분리해 이후 문구
변경이 제어 로직을 건드리지 않게 한다.

### 4.2 계좌 스냅샷

`AccountSummary`에 `deposit` 필드를 추가한다. `OperationsControl`은 기존
`get_deposit()` 결과의 `total`과 `available`을 같은 기준 시각의 스냅샷에
보존한다. `get_deposit()` 실패 시 두 값 모두 `None`이며 실패 원천은 기존
`deposit` 실패 항목 하나로 유지한다.

총자산은 데이터 모델에 거짓 숫자를 넣지 않는다. 프레젠터가 검증된 필드가
없다는 사실을 `확인 불가`로 표시한다.

## 5. 공통 표시 규칙

### 5.1 금액

- 양수: `1,250,000원`
- 음수: `-12,300원`
- 0: `0원`
- 누락: `확인 불가`
- 실현손익 정확도 `estimated`: `추정`

불리언을 정수로 잘못 표시하지 않도록 `bool`은 금액 입력으로 허용하지
않는다. 예상하지 못한 타입은 예외로 전체 명령을 실패시키지 않고
`확인 불가`로 표시한다.

### 5.2 시각

timezone-aware `datetime`과 ISO-8601 문자열을 Asia/Seoul로 변환해
`YYYY-MM-DD HH:MM:SS KST`로 표시한다. timezone 정보가 없거나 파싱할 수
없는 값은 원문을 노출하지 않고 `확인 불가`로 표시한다.

### 5.3 상태

내부 영문 상태는 다음 운영자 의미로 바꾼다.

- idle: `대기`
- running: `실행 중`
- paused: `일시정지`
- succeeded: `완료`
- failed: `실패`
- needs_attention: `확인 필요`
- accepted/in_progress: `처리 중`

새롭거나 알 수 없는 상태는 정상으로 간주하지 않고 `확인 필요`로 표시한다.

## 6. 명령별 출력 계약

### 6.1 `/status`

정상 예시는 다음과 같다.

```text
✅ 시스템 정상

📅 자동 일정  운영 중
📈 자동매매  대기
📦 관리 포지션  0개
🤖 Telegram  정상
📨 대기 메시지  0건

최근 확인  2026-07-26 00:06:00 KST
```

다음 중 하나라도 참이면 최상위 상태를 `⚠️ 시스템 주의` 또는
`🚨 시스템 장애`로 승격하고 관련 원인만 표시한다.

- 스케줄러 또는 Telegram 서비스 `dead`
- poller, command, reconciliation loop `dead`
- sender outbox `dead`
- Telegram degraded 또는 backoff
- dead letter 1건 이상
- kill switch 활성

내부 run ID는 정상 화면에서 숨긴다. 장애 진단이나 활성 거래가 있을 때만
필요한 범위에서 표시한다.

### 6.2 `/account`

```text
💰 계좌 요약

예수금          10,000,000원
주문 가능        9,979,053원
보유주식 평가            0원
총자산              확인 불가

평가손익                0원
오늘 실현손익            0원 (추정)

기준  2026-07-26 00:06:00 KST
```

공백 정렬은 읽기 보조일 뿐 데이터 계약이 아니다. 값이 길어져도 잘리지
않는다. 조회 실패가 없으면 출처와 실패 항목은 숨긴다. 일부 소스가 실패하면
`⚠️ 일부 정보를 불러오지 못했습니다`와 `예수금`, `잔고`,
`오늘 실현손익` 중 실패한 한국어 항목만 추가한다.

`총자산 확인 불가`는 오류가 아니라 현재 정확도 계약을 드러내는 정상
표시다.

### 6.3 `/positions`

포지션이 없으면 다음처럼 표시한다.

```text
📦 관리 포지션

현재 관리 중인 포지션이 없습니다.
```

포지션이 있으면 종목별 블록에 종목코드, 한국어 상태, 수량, 평균 진입가를
표시한다. 현재 `TradingStore` 계약에 종목명과 브로커 현재가가 없으므로
이를 추정하거나 추가 호출하지 않는다. 손상 행이 0이면 숨기고, 1 이상이면
경고와 건수만 표시하며 손상 원문은 노출하지 않는다.

### 6.4 `/help`

```text
🤖 OhMyStock 명령어

조회
/status     시스템 상태
/account    계좌와 손익
/positions  관리 포지션

제어
/pause      자동 일정 일시정지
/stop       신규 진입 중지

확인 필요
/resume          자동 일정 재개
/liquidate_all   관리 포지션 전체 청산
```

`/confirm`은 BotFather 메뉴에서 직접 사용하는 일반 명령처럼 안내하지 않고,
확인 요청 응답에 생성된 전체 명령을 그대로 제공한다.

### 6.5 제어와 확인 응답

- 성공: `✅ 완료`와 실제 변경된 상태
- 확인 대기: `⚠️ 확인 필요`, 영향, 만료 전 실행할 `/confirm ...`
- 적용 불가: `⚠️ 적용하지 못했습니다`, 안전한 이유와 현재 상태
- 실패 또는 복구 불명: `🚨 처리 결과를 확인해야 합니다`

`/stop`은 신규 진입만 중지하며 기존 포지션 감시는 계속된다는 사실과
재기동·다음 거래일의 복귀 가능성을 유지한다. `/liquidate_all`은 관리
포지션만 대상으로 한다는 사실을 명시한다. 표시 변경 때문에 상태 변경
명령을 재실행하거나 기존 confirmation fingerprint 계약을 바꾸지 않는다.

## 7. 오류와 보안

- 누락값과 예상하지 못한 표시 타입은 `확인 불가`로 축소한다.
- 알 수 없는 상태를 정상으로 표시하지 않는다.
- 종목명, 오류 원문, 브로커 응답 원문을 그대로 렌더링하지 않는다.
- 계좌 응답은 기존처럼 민감 outbox로 저장하고 TTL 삭제 대상에 둔다.
- 금액, 확인 토큰, bot token이 로그에 남지 않는 기존 회귀를 유지한다.
- Telegram 상관 ID 헤더와 조각 순번은 변경하지 않는다.

## 8. 테스트와 수용 기준

### 8.1 프레젠터 단위 테스트

- 양수, 음수, 0, 누락, 잘못된 타입 금액
- UTC와 다른 timezone 입력의 KST 변환
- timezone 없는 시각과 잘못된 ISO 문자열
- 정상 상태 압축
- 각 dead/degraded/backoff/kill switch/dead letter 경고 승격
- 알 수 없는 상태의 `확인 필요` 처리
- 계좌 전체 성공과 각 부분 실패
- 빈 포지션, 복수 포지션, 손상 행
- help와 모든 제어 성공·확인·실패 문구

### 8.2 통합·회귀 테스트

- `CommandProcessor`가 프레젠터를 통해 기존 명령 결과를 발행한다.
- confirmation 원문 전체가 ephemeral 응답으로만 전달된다.
- durable intent 상태와 감사 결과가 표시 변경 전과 동일하다.
- 명령 응답 경로에서 token, confirmation, 계좌 금액이 로그에 남지 않는다.
- 4,096자 제한, 상관 ID, 조각 재시도 계약이 유지된다.

### 8.3 완료 조건

- 관련 테스트와 전체 비라이브 회귀가 통과한다.
- 구현 회고에 실제 수용에서 발견한 의미 차이, 설계 판단, 파일 위치,
  검증 결과를 기록한다.
- 네 상시 리뷰어가 같은 diff를 독립 검토하고 Critical/Important가 0이다.
- 키움 어댑터와 TR 호출부를 변경하지 않으므로 broker-api-expert는 기본
  범위에 포함하지 않는다. 구현 중 해당 경계를 건드리게 되면 즉시 추가한다.
- 실제 Telegram 재수용은 코드 배포 승인 후 `/status`, `/account`,
  `/positions`, `/help` 조회 명령만 수행한다. 상태 변경 명령은 별도 승인
  없이 실행하지 않는다.
